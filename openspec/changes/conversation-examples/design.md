# Design

## Context

`/api/chat` returns `{reply, cards, trace}`; `trace.steps` lists each tool call with `tool`, `arguments` and an
`outcome` summary (`products` count, `order`, or `error` code). The rate limiter (10 requests per minute per IP) is a
FastAPI dependency, `chat_rate_limiter`. CI uses `tests/fakes.py` and never reaches Gemini. Reference date is
2026-03-23, so no delivered order is inside the 7-day regret window: order 7 (Letícia Gonçalves Rocha, delivered
2026-02-17) has regret and defect windows closed and the legal warranty open until 2026-05-18, which is the
non-trivial case the example shows.

## Goals / Non-Goals

**Goals:** a cheap, repeatable real-model check of tool selection and arguments; examples that are regenerated by
the same code, not pasted by hand.

**Non-Goals:** statistical evaluation, wording or factual checks of the prose, a server process for the run.

## Decisions

### D1. In-process `TestClient(app)` instead of HTTP to a running server

The script imports `api.index.app` and posts with FastAPI's `TestClient`, so it runs the real validation, agent loop,
cards and trace without `uvicorn` or `vercel dev`. `app.dependency_overrides[chat_rate_limiter]` returns a limiter
with a high limit, so ~20 requests in a run are not rejected. Alternative: calling `run_turn` directly. Rejected:
it skips the response models, which are what the UI consumes. Alternative: pointing at the deployed URL. Rejected:
the production rate limit would block the run and the prompt change must be checked before deploy.

### D2. Cases and examples as data, checks as pure functions

One module, `scripts/record_examples.py`. Each turn is a small dataclass: `text`, `locale`, and a tuple of
`ExpectedCall(tool, args, outcome)`. Argument matchers stay minimal: `Contains(words)` (normalized, every word
present, for `name`), `AtMost(value)` (for `max_price`) and plain equality (category, `order_id`). Keys not listed
are not checked, so extra filters such as `only_available` do not fail a turn. `check_turn(expected, trace) ->
list[str]` returns problems (empty means pass), and `render_example(...) -> str` builds the Markdown. Both are pure
and tested in `tests/test_record_examples.py` with fixture traces (`pytest.ini` already has `pythonpath = .`, so
`scripts.record_examples` imports as a namespace package). The `main()` that loads `.env`, calls the model and
writes files is not unit tested.

### D3. Example layout

Files `examples/01-acoustic-guitars.md`, `02-takamine-gd20-price.md`, `03-regret-return.md`,
`04-address-and-strings.md`, `05-english.md`. Header: title, what it shows, model, reference date, recording date.
Per turn: `**Customer:**`, `**Agent:**` (reply as is) and a `Tools:` bullet per step (`search_products` +
compact JSON arguments + outcome), or "no tool call". Cards are not rendered: the tool lines already show the data
source, and full card JSON would bury the conversation. A conversation is written only if all its turns pass.

The regret example: turn 1 "Comprei um violão no pedido 7 e me arrependi, posso devolver?" expects no tool (the
agent must ask for name or email); turn 2 gives the full name and expects `get_order_status` with `order_id` 7.

### D4. Prompt wording

Three additions in Portuguese, in the existing sections of `PROMPT_TEMPLATE`:

- "Quando usar cada fonte": use `category`, `min_price`/`max_price` and `only_available` whenever the question
  gives them (for "violões até R$ 1000", category Violões and `max_price` 1000).
- "Regras de ouro": copy prices, PIX price, installments and dates character for character as the tool returned
  them (`599.9` is "R$ 599,90", never "R$ 599,00" or "cerca de R$ 600").
- New "# Formato" section: short paragraphs, `**negrito**` for highlights, lists with "- "; no headings, tables,
  numbered lists or links.

Prompt tests check for the stable fragments (`category`, `max_price`, `only_available`, "exatamente", "- ") rather
than whole sentences, so wording can be tuned without rewriting tests.

### D5. Exit status and output

One line per turn, `PASS` or `FAIL <case>: <problems>`; failures also print the trace steps. Exit 1 if anything
failed, 2 if the key is missing. A free-tier `503 model_unavailable` counts as a failure; the user reruns.

## Risks / Trade-offs

- [The model is not deterministic, a case can flip between runs] → checks look only at tool name and key
  arguments; the run is repeated before recording and the result is noted in tasks.
- [Prompt rules reduce but do not remove misquotes] → cards stay the source of truth; the README limitation stays,
  reworded with what the run showed.
- [Free-tier quota or 503 during a run] → ~20 calls per run, well under daily limits; rerun on failure.
